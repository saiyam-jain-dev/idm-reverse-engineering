Observed static architecture
----------------------------
1. Browser injection:
   * Current Edge and Firefox packages inject content.js at document_start in
     all frames for HTTP, HTTPS, FTP, and file URLs. Current Chrome declares
     *://*/* and all frames.
   * The content script checks for Windows, gates to HTML documents, connects
     to the extension background using a named runtime port, and registers
     document, pointer, keyboard, and page lifecycle events.
   * Static code contains video/audio/object/embed selectors, MutationObserver
     use, page/player-specific selector patterns, and code that observes media
     DOM changes. This supports media discovery as a static capability; it
     does not establish which sites or selectors worked at runtime.
   * document.js contains wrappers around page fetch/XHR/response-reading
     paths and sends candidate data through a window-message bridge to the
     content script. The static parser reports these scripts were read as
     inert text; bootstrap code was not run.
   * Focused Edge source review confirms the content script counts video/audio
     elements, scans and tracks video elements, and uses DOM mutation observers.
     It also observes inline script text and has a path that can issue a text
     XMLHttpRequest for a discovered URL before sending compact numeric
     messages to the extension background. The protocol meaning of those
     numeric message IDs is not fully recovered.
   * A literal-token search of Edge content.js, document.js, and background.js
     found no "quality" token. No complete quality/variant list or user-facing
     IDM video-panel renderer was identified in the extension sources. The
     extension may detect/forward media candidates while desktop IDM or
     site-specific runtime data determines selectable variants; this remains
     an unverified hypothesis, not a finding.

2. Download interception and request context:
   * The background registers webRequest listeners for before-request,
     before-send-headers, headers-received, response-started, and errors.
     Chrome additionally registers completion/redirect observers in the
     analyzed code path.
   * Request-body capture is requested on matching URL/type filters.
   * The downloads.onCreated path can pause a browser download, correlate it
     with a webRequest, then pass it to the desktop-side protocol. The
     determining-filename handler filters using extension and URL rules
     before forwarding; it does not blindly take over every browser download.
   * The code reads URL-specific cookies, serializes cookie name/value pairs,
     and constructs download context containing URL/referrer/frame context,
     user agent, cookies, request/response headers, and POST data where
     available. The exact serialization is protocol-specific and obfuscated.
   * The package maps many MIME types/extensions, including media and streaming
     playlist/manifest formats such as M3U8, MPD, and F4M.
   * Context-menu definitions include downloading links/media, selected text,
     page content/all links, and items on the browser downloads page.
   * Browser downloads API listeners are used for created downloads and
     filename determination where supported.

3. Extension-to-desktop bridge:
   * All current extension variants contain a WebSocket connection attempt to
     127.0.0.1:1001 and 0.1.0.1:1001, using the subprotocol
     plugin.v3.internetdownloadmanager.com and a client/random query string.
   * On connection failure the extension falls back to
     browser.runtime.connectNative("com.tonec.idm"), then retries with
     backoff. These are static code paths, not observed live connections.
   * Chrome/Edge native host manifest is IDMMsgHost.json. It declares host
     com.tonec.idm, stdio transport, executable IDMMsgHost.exe, and two allowed
     extension IDs:
     ngpampappnmepgilojfohadhhmbhlaek
     llbjbkhnmlidjebalopleeepgdfgcpec
   * Firefox uses IDMMsgHostMoz.json and allows only
     mozilla_cc3@internetdownloadmanager.com.
   * Windows native-messaging registry entries point Chrome and Edge to
     IDMMsgHost.json and Mozilla to IDMMsgHostMoz.json. Entries were observed
     in current-user hives; Chrome also has machine-wide entries.
   * The native host manifest and registration establish a declared bridge,
     not that a browser extension is enabled or that the native host is
     currently running.

4. Permissions and disclosed handling:
   * Current Edge MV2 and Firefox MV2 request <all_urls>, cookies, tabs,
     contextMenus, webNavigation, webRequest, webRequestBlocking,
     nativeMessaging, and related permissions. Firefox additionally lists
     privacy and idle.
   * Chrome MV3 uses a service_worker, minimum Chrome 109, host_permissions
     <all_urls>, and declares scripting, webRequest, declarativeNetRequest,
     downloads, cookies, tabs, nativeMessaging, and related permissions.
   * Chrome's MV3 background contains declarativeNetRequest session-rule
     creation for configured URL patterns that redirect into the extension's
     captured.html route. Since the matching pattern arrives as runtime
     configuration, the complete active rule set is not statically known.
   * Firefox welcome/privacy HTML says request data required to transfer
     downloads to IDM can include URL, address, cookies, encrypted
     credentials, query parameters, and POST data; it states the data is
     stored locally until the download is deleted and resent to the original
     server, not to IDM/vendor or third-party servers. This is a static policy
     statement, not a verified runtime traffic finding.

5. Cross-browser/version observations:
   * Desktop IDMan.exe reports 6.43.2.2; current extension manifests report
     6.43.1; IDMMsgHost.exe reports 6.38.20.9. IDMNetMon.dll reports
     6.43.2.363 and idmbrbtn.dll reports 6.43.1.100. These component version
     differences are observed, but do not by themselves prove incompatibility
     or a defect.
   * Chrome is the current MV3/service-worker package; Edge and Firefox
     packages are MV2. A REA comparison between Edge and Chrome graphs reported
     6 changed items and 41 unknown items (comparison ID below); graph
     coverage is incomplete, so do not treat this as an exhaustive diff.
   * Direct package comparison found document.js has the same SHA-256 in
     current Edge, Chrome, and Firefox extractions; background.js and
     content.js differ across browser packages.

Chrome extension follow-up (REA static review)
---------------------------------------------
* The installed IDMGCExt.crx is a Chrome Manifest V3 package, version 6.43.1,
  minimum Chrome 109. Its manifest declares a service worker, all-site host
  permissions, all-frame content injection at document_start, and permissions
  including cookies, webRequest, downloads, declarative network rules, and
  native messaging.
* In background.js, the code registers downloads.onCreated and filename
  determination handlers and observes request, request headers, response
  headers, response start, and error events. Some listeners request POST body
  data. A download can be paused and correlated with request state before the
  desktop bridge handles it. Configured URL patterns can install session
  declarativeNetRequest redirects to captured.html.
* The desktop bridge tries WebSockets to loopback 127.0.0.1:1001 and
  0.1.0.1:1001 with a product-specific subprotocol, then falls back to the
  com.tonec.idm native messaging host. This is a static code path, not evidence
  that either endpoint or host was active.
* content.js establishes top/sub-frame runtime ports, scans video/audio and
  related media elements, monitors DOM mutations, contains player/site selector
  patterns, observes inline scripts, and sends structured numeric messages to
  the background. document.js uses a same-origin window-message bridge for
  page-context instrumentation. These observations establish static
  capabilities, not runtime success or exact message semantics.
* The static extension evidence does not establish where IDM renders video
  quality choices or how stream variants are generated. That pipeline and
  native IDM processing remain unresolved; no DRM or site-specific stream
  reconstruction was inferred.
* The manifest and static handlers permit processing of URLs, cookies,
  request/response headers, and POST metadata for download handoff. This is a
  static capability description; live collection/transmission was not observed.

Independent Chrome extension prototype
---------------------------------------
* Source is in chrome-extension/. It is an original Manifest V3 implementation
  and does not include IDM code, icons, or assets.
* It sends direct HTTP(S) URLs and explicit link/video/audio context-menu
  actions to the Windows desktop queue. It offers an active-tab media scan
  only when the user clicks the popup scan control.
* It requests activeTab, contextMenus, downloads, nativeMessaging, scripting,
  and storage. It has no all-sites host permission, cookie permission, or
  request-body/header observers.
* The native host uses Chrome stdio framing and forwards one request to a
  same-user named pipe. The WinForms server uses PipeOptions.CurrentUserOnly,
  bounded JSON frames, a bounded concurrent-client count, and dispatches queue
  actions onto the UI thread. The host is registered per-user in Chrome's
  NativeMessagingHosts registry key and its manifest allowlists only the
  extension's fixed ID.
* The app and host are published side-by-side in
  bin\Release\net8.0-windows\win-x64\publish\BridgeReady\; the installer is
  chrome-extension\install-native-host.ps1. The bridge was exercised end to
  end with status/list requests through the published native host and pipe;
  the response reported the desktop ready and omitted URL/path fields. The
  test-launched desktop process was stopped afterward.
* Media scanning reads direct video/audio/source element URLs. It explicitly
  marks HLS/DASH manifests unsupported and does not claim to reconstruct video
  quality variants or protected media.
* Chrome installation steps, permission rationale, and limitations are in
  chrome-extension/README.md. Browser interception uses downloads.onCreated
  to pause a new Chrome HTTP(S) download, ask the desktop app to show a native
  confirmation dialog, then cancel Chrome and start the desktop queue only
  after acceptance. Choosing Chrome or encountering a handoff failure resumes
  the browser item if Chrome has not already been cancelled. The desktop queue
  commit retries once and is idempotent; if both commit attempts fail after
  Chrome cancellation, the job remains queued for manual start. The popup
  toggle is on by default.
* Browser metadata is handed off as URL plus suggested filename; browser
  cookies, POST bodies and request headers are not copied. The desktop
  downloader may fail on authenticated or POST-backed downloads. Since
  downloads.onCreated fires after Chrome starts the transfer, the pause is
  best-effort and very fast downloads can finish before the extension can
  intercept. This is not a pre-request blocking hook.
* Node tests cover automatic handoff, disabled interception, choosing Chrome,
  unavailable native host, and browser cancellation failure, along with the
  existing controls and URL validation; the suite has 12 passing cases. The
  published native host and desktop app were also exercised with a
  download.intercept request: the custom prompt appeared and choosing
  **Keep in Chrome** returned decision=browser. The extension was not loaded
  into Chrome, so this is not a live browser download test.

* In background.js, the download setup function registers Chrome's
  downloads.onCreated listener and request/response webRequest listeners. The
  download-created handler checks runtime configuration and URL eligibility,
  correlates a candidate with cached request state using URL and start time,
  records it by Chrome download ID, then calls downloads.pause. A handoff
  completion helper clears that record and chooses downloads.cancel or
  downloads.resume. The extension's desktop transport tries its loopback
  WebSocket before the com.tonec.idm native-messaging host. The complete
  request-metadata correlation is not recovered.
* The independent implementation uses a narrower version of this lifecycle:
  pause -> desktop confirmation -> cancel Chrome and start the desktop queue
  if accepted; otherwise resume Chrome. The desktop prompt presents the
  suggested filename and source, with **Download here** and **Keep in Chrome**
  actions. Chrome must be reloaded and the newly requested downloads/storage
  permissions accepted before this code runs. Chrome cancellation precedes
  the desktop queue commit; failed commits are retried once and can be started
  manually from the desktop queue. This update has not been tested in a live
  Chrome profile.

Limitations and next steps
--------------------------
* REA's PE disassembly provider is unavailable on this host. Ghidra is not
  configured (GHIDRA_INSTALL_DIR unset); Hopper is unsupported on Windows;
  IDA MCP and Kuna are not configured, and Kuna does not admit PE targets in
  this reported profile. REA binary_overview and string search therefore
  failed with provider_unavailable. No native IDMan function pseudocode or
  call graph has been obtained.
* Do not install/configure an analysis provider without explicit approval.
  To continue native code analysis, configure an existing supported provider
  or agree on a Ghidra installation/configuration plan first.
* Browser runtime was not observed. The user requested this follow-up, but REA
  still needs a caller-supplied loopback CDP endpoint and selected target for
  passive browser inspection. No browser navigation, extension action,
  network capture, or page data was performed.
* Browser extension packages in the IDM install folder and native host
  registration were observed; actual browser extension enablement/state was
  not checked.
* Application-graph parsing is static and incomplete. The analyzer reports
  unresolved dynamic edges, omitted inline JavaScript in captured.html, and
  substantial semantic unknowns. A no-match feature trace does not establish
  feature absence.
* CRX/NEX archive analysis used a derived ZIP payload after removing the CRX3
  wrapper. The original package SHA-256 is recorded above; the derived ZIP has
  a different SHA-256 and is not the signed package itself.
* A future pass should obtain a loopback CDP endpoint and selected existing
  video page, passively inspect its DOM/UI and attach-window event metadata,
  then reconcile only user-approved observations with the static application
  graph. A separate native pass should examine IDMan.exe,
  IDMMsgHost.exe, IDMNetMon.dll, and IDMIntegrator64.exe once a supported PE
  provider is available.

Feature audit from source, cross-checked against the managed artifact:
* Direct HTTP(S) file downloads, a sequential queue, queue persistence,
  progress/status fields, pause/resume/retry/cancel, categories/filters, and
  opening completed files/folders are implemented in source. The transfer
  engine writes a .part file, attempts a Range request when resuming, checks
  the returned range start, and restarts from zero when the server ignores a
  Range request. These are static implementation observations; no real
  download was executed during this audit.
* Newly submitted desktop downloads now call StartQueue. Queued jobs restored
  at application launch also auto-start. Explicitly Paused jobs stay paused
  and require Resume. Browser-intercepted jobs still wait for the browser's
  cancellation/handoff confirmation before queue execution.
* Confirmed defect fixed: queued/paused cancellation and Stop all previously
  ignored partial-file deletion failure and could mark a download Cancelled
  while its .part file remained. An active cancellation had the same issue.
  Failed cleanup now leaves the affected job Paused, preserves its partial
  file for inspection/resume, and surfaces the cleanup error instead of
  reporting successful cancellation. Stop all preserves the affected paused
  state and reports that cleanup failed.
* The extension's automated mock-Chrome suite passes 12/12. The desktop
  project builds with 0 warnings and 0 errors. This does not verify actual
  Chrome interception, desktop UI interactions, or transfer behavior against
  a live HTTP server.

Features deliberately not implemented / bounded:
* Segmented/parallel downloads, login/cookie/header/POST transfer context,
  scheduler automation, video/stream quality selection, and HLS/DASH
  reconstruction are not supported. The browser interceptor is best-effort:
  Chrome exposes downloads.onCreated after a transfer starts, and browser
  authentication/request context is not copied.
* A successful source build is not proof the published desktop EXE is the one
  a user currently launches. Confirm the EXE path/version when diagnosing a
  persistent UI symptom; other copies can be stale.
* No ordinary desktop-app test project currently exercises queue transitions
  or the transfer engine. Add focused tests and run controlled local HTTP
  cases (success, 404, cancellation, range-supported resume, ignored Range,
  and invalid range) before treating these paths as runtime-verified.
